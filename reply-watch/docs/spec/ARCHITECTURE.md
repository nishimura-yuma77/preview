# アーキテクチャ：用件管理

| 担当 | 責務 |
| --- | --- |
| Slack ブリッジ | Slack イベントと送信結果を解釈し、対象会話と操作（返信待ち／完了）を決める。会話から連携元ID、表示名、参照 URL、発生時刻を組み立てる。 |
| reply-watch（Node.js） | 連携元ID（`source_id`）で対象を検索し、発生時刻に基づいて状態を保存する。返信待ちの表示名と参照 URL を一覧で返す。連携元IDは不透明な文字列として扱う。 |
| nginx / ブラウザ | HTTPS と Basic 認証で一覧を提供する。ブラウザは5秒間隔で再取得し、失敗時には直前の一覧を維持して更新エラーを表示する。 |

## ブリッジが操作を選ぶ条件

起点は既存の受付条件を満たす `@Bot` 宛ての依頼。ブリッジはその会話が受理済みであることを再起動後も保持する。連携元IDは `slack_{ワークスペースID}_{チャンネルID}_{親投稿時刻}` とする。親投稿時刻は `thread_ts ?? ts` の文字列の `.` を `_` に置換する（例：`slack_T123_C456_1800000000_000001`）。最終回答と人の返信は同じ親投稿を指すため、用件IDとの対応表は不要である。

| 対象スレッドで起きたこと | 内部 API に渡す操作 |
| --- | --- |
| Bot の最終回答の投稿成功 | `pending`。表示名は `#チャンネル名`、参照 URL は回答のパーマリンク。分割回答は全体の投稿成功後に末尾の投稿を使う。 |
| 人の新規返信 | `done`。投稿者やメンションの有無を問わず、作業依頼の権限判定とは独立して扱う。 |
| Bot の再回答の投稿成功 | 同じ `source_id` で `pending`。最新の回答へのリンクに差し替える。 |

無関係な会話、進捗通知、他 Bot の投稿、編集・削除、リアクションは操作の対象外。発生時刻には回答・返信そのものの投稿時刻を Unix マイクロ秒に変換して使い、一時的な送信失敗時は同じ `source_id`・時刻・内容で再送する。

## 用件の更新規則

`source_id` の一意制約を使い、用件の特定、発生時刻の比較、保存を単一トランザクションで行う。未登録なら SQLite が整数の `id` を自動採番する。登録済みなら既存行を更新し、完了・再開・再送でも `id` は変わらない。

| 条件 | 結果 |
| --- | --- |
| 初回、または保存値より新しい `pending` | 返信待ちとして保存し、表示名・URL を今回の値にする。 |
| 初回、または保存値より新しい `done` | 完了として両ID・時刻を残し、表示情報を消す。初回が完了でも、その後に遅れて届く古い返信待ちを抑止できる。 |
| 保存値より古い操作、または同じ操作の再送 | 変更なし。 |
| 同時刻で異なる状態 | 配送順によらず完了を優先する。 |

## 配置とアクセス境界

`/srv/reply-watch/` は `/srv/previews/` の隣に置く。nginx への読取専用マウントは `public/` のみ。`/task`、静的資産、`GET /task/api/pending` は Basic 認証で保護し、一覧は `no-store` とする。内部 API は同一ホストのブリッジからループバック経由で直接呼び、専用 Bearer トークンを検証する。nginx がアプリへ転送するのは一覧の GET のみ。

| 相対パス | 内容 |
| --- | --- |
| `src/server.mjs`・`src/routes.mjs` | Node.js の起動と HTTP 境界 |
| `src/task-service.mjs`・`src/task-store.mjs` | 用件の更新規則と SQLite アクセス |
| `public/` | 一覧画面 |
| `migrations/`・`data/tasks.sqlite` | スキーマ変更と非公開の実行時データ |
